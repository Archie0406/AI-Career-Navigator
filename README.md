# Career Path Navigator

A Data Science project by a third-year B.Voc AI & Data Science student. It predicts a likely career category from a person's skills, interests, education, and years of experience, and shows a full, honest machine learning workflow behind that prediction.

> For a deeper dive into *why* each technique was chosen, see [METHODOLOGY.md](METHODOLOGY.md). This README stays intentionally simple — the goal is to be able to explain every line of it in an interview.

---

## 1. Project Overview

The app takes a person's skills, interests, education, and experience, and:
1. Predicts the most likely career category using a trained ML classifier
2. Shows how confident the model is in that prediction
3. Shows which of the person's skills match the predicted career, and which common skills they're missing
4. Suggests a simple, rule-based year-by-year roadmap for that career
5. Lets the person try a "what-if": add a skill and see if the prediction changes

## 2. Problem Statement

Choosing a career path is hard, especially for students who don't know which of their skills line up with which job roles. This project explores whether a simple, interpretable machine learning model can classify a person into a likely career category based on their skills, interests, education, and experience — and whether it can explain *why*, not just output an answer.

## 3. Objectives

- Build a small but complete, correctly-evaluated ML classification pipeline
- Compare multiple standard algorithms fairly, using proper train/test methodology
- Be transparent about what is genuinely ML-driven vs. what is a simple rule/dataset lookup
- Practice explaining every technique used, in plain language

## 4b. How Skill/Interest Overlap Was Built (why this isn't a trivial dataset)

An earlier version of this dataset (720 rows, 80 per career) drew each career's skills from an almost completely separate vocabulary — about 90% of most careers' skill tokens never appeared under any other career label. That made the 9-way classification problem close to trivial. The current dataset (`model/generate_dataset.py`) fixes this at the source using three token pools per row:

1. **Primary pool** — skills common in that career, but a given row only gets 0–2 of them (sometimes zero, deliberately — a real candidate's listed skills aren't always the "obvious" ones for their role)
2. **Overlap pool** — skills shared between two realistically adjacent careers (e.g. Data Analyst ↔ Business Analyst share `sql`, `excel`, `dashboards`; Machine Learning Engineer ↔ Software Engineer share `python`, `algorithms`, `git`)
3. **Universal pool** — soft/general skills that show up everywhere (`communication`, `git`, `agile`, ...)

On top of that, ~55% of rows get one extra "noise" skill drawn from a **random, not-necessarily-adjacent** career's primary pool, and ~35% get a noise interest the same way — modeling the fact that real candidates sometimes have an odd skill that doesn't fit their career at all. No career name is ever written into the skills/interests text itself, so there is no literal target leakage — the realism comes from vocabulary overlap, not from hiding the label.

### Class Imbalance Analysis

The dataset is deliberately imbalanced (see Section 4's distribution table). This matters for two reasons covered later in this README:
- **Accuracy alone can be misleading** on imbalanced data — a model could score well just by favoring the majority classes (Software Engineer, Data Analyst) while doing poorly on minority ones (UX Designer, Product Manager). This is why **Macro F1** (Section 13) is reported alongside accuracy and weighted F1.
- It makes **class weighting** (Section 13b) a genuine, non-trivial experiment rather than a formality — with a perfectly balanced dataset, `class_weight="balanced"` has nothing to correct for.

## 7. Feature Engineering

Three different techniques are used, one per feature type — each chosen because it's the standard, simplest correct tool for that data type:

| Feature | Type | Technique | Why |
|---|---|---|---|
| `skills` | Text | TF-IDF (unigrams + bigrams) | Turns skill phrases into weighted word counts, so "python, sql" can be compared numerically against other people's skill text. TF-IDF down-weights very common words and up-weights distinctive ones. |
| `interests` | Text | TF-IDF (its own separate vectorizer) | Same idea as skills, but kept in a **separate** TF-IDF vectorizer so skill words and interest words don't compete for the same vocabulary space. |
| `education` | Categorical | One-Hot Encoding | Education levels (12th Pass, Diploma, Bachelor's, Master's, PhD) have no single meaningful number — one-hot encoding turns each into its own 0/1 column instead of implying a false numeric order. |
| `experience` | Numeric | StandardScaler | Experience is already a number (years), so it doesn't need encoding — but scaling it to zero-mean/unit-variance stops it from being over- or under-weighted purely because of its raw numeric range compared to the other features. |

All four are combined using scikit-learn's `ColumnTransformer`, so each column gets exactly the right treatment in one pipeline:

```python
ColumnTransformer([
    ("skills_tfidf",    TfidfVectorizer(ngram_range=(1, 2), max_features=3000), "skills"),
    ("interests_tfidf", TfidfVectorizer(ngram_range=(1, 2), max_features=2000), "interests"),
    ("education_ohe",   OneHotEncoder(handle_unknown="ignore"), ["education"]),
    ("experience_num",  StandardScaler(), ["experience"]),
])
```

## 8. Data Preprocessing / Train-Test Split

- Data is split **80% train / 20% test** using `train_test_split(..., stratify=y)`, so every career category keeps the same proportion in both sets
- **Why stratify?** With 9 classes, a plain random split could by chance put too few (or zero) examples of a smaller class into the test set, making that class's metrics unreliable. Stratifying keeps each class's proportion consistent across train and test, so every class gets a fair, representative test sample.
- `random_state=42` is fixed everywhere, so results are reproducible
- The test set (144 rows) is **never touched** during training or model selection — it's only used once, at the very end, to report final metrics

**Avoiding data leakage**: All preprocessing (TF-IDF vectorizers, One-Hot Encoder, StandardScaler) lives *inside* the scikit-learn `Pipeline`/`ColumnTransformer`, and a fresh, unfitted preprocessor is built for every model. This means `.fit()` is only ever called on `X_train` — the vectorizers' vocabulary, the scaler's mean/std, and the encoder's categories are all learned exclusively from training data, then just *applied* (`.transform()`) to the test set and to new predictions. The test set's data never influences how any feature is built. This is checked directly in the code (`model/train_model.py`'s `create_model_pipelines()` builds a new `ColumnTransformer` per pipeline, and `final_model.fit(X_train, y_train)` is the only place `.fit()` is called on the full pipeline).

## 9. Machine Learning Models

Three standard supervised classification algorithms are compared, using scikit-learn's **default hyperparameters** for a fair first comparison:

1. **Logistic Regression** — a linear model; fast, interpretable, and exposes per-feature weights directly
2. **Random Forest** — an ensemble of decision trees; can capture non-linear patterns
3. **Linear SVM** (Support Vector Machine, linear kernel) — finds the widest possible margin between classes; strong for high-dimensional text features like TF-IDF

No deep learning, no neural networks, no boosting libraries (like XGBoost) — the point of this project is to demonstrate solid understanding of standard supervised ML, not to chase the newest algorithm.

## 10. Model Comparison

All three models are trained on the same data and compared on the same held-out test set:

| Model | Accuracy | Precision (weighted) | Recall (weighted) | F1 (weighted) | Precision (macro) | Recall (macro) | F1 (macro) | CV Mean |
|---|---|---|---|---|---|---|---|---|
| Logistic Regression | 0.9615 | 0.9623 | 0.9615 | 0.9615 | 0.9614 | 0.9608 | 0.9607 | 0.9574 |
| **Random Forest** | **0.9615** | 0.9630 | 0.9615 | **0.9616** | **0.9640** | 0.9601 | **0.9613** | **0.9581** |
| Linear SVM | 0.9560 | 0.9574 | 0.9560 | 0.9561 | 0.9561 | 0.9574 | 0.9560 | 0.9485 |

*(Live numbers — regenerate anytime with `python -m model.train_model`; see `model/evaluation_results.json` for the exact current run.)*

**Why Random Forest was selected**: Logistic Regression and Random Forest tied on test accuracy (0.9615), so the tie was broken using cross-validation mean — Random Forest's 0.9581 edged out Logistic Regression's 0.9574. Random Forest also had the best macro F1 (0.9613), meaning it wasn't just doing well on the big classes — it held up on the smaller ones (UX Designer, Product Manager) too. Linear SVM was close behind on all metrics. A **confusion matrix** (`static/confusion_matrix.png`, also on `/evaluate`) shows the actual 14 test-set errors are concentrated almost entirely between careers that were deliberately built to share vocabulary (e.g. Back-End Developer ↔ DevOps Engineer, Data Analyst ↔ Machine Learning Engineer) — see Section 14 (Error Analysis).

## 11. Cross-Validation

**5-Fold Stratified Cross-Validation** is used to check that model performance is consistent, not a fluke of one particular train/test split.

> Cross-validation helps us check whether the model performs consistently across different subsets of the training data.

In practice: the training data is split into 5 folds, the model is trained on 4 and validated on the 5th, five times (rotating which fold is held out), and the 5 accuracy scores are averaged. "Stratified" means each fold keeps the same career-category proportions as the full (imbalanced) dataset.

**Current result** (Random Forest, the deployed model): CV mean = 0.9581, std = 0.0033 — low variance across folds, meaning the model's performance isn't a fluke of one particular split.

## 12. Hyperparameter Tuning

A small, deliberately simple `GridSearchCV` demonstration was run — tuning just **one hyperparameter** (`C`, the regularization strength) for **one model** (Logistic Regression), regardless of which model ultimately wins the comparison:

```python
param_grid = {"clf__C": [0.1, 1, 5, 10, 20]}
GridSearchCV(pipeline, param_grid, cv=5, scoring="accuracy")
```

**What `C` means**: Logistic Regression balances fitting the training data against keeping its weights small (regularization). `C` is the *inverse* of regularization strength — small `C` = more regularization (simpler model), large `C` = less regularization (fits training data more closely). Hyperparameters like `C` are chosen *before* training and searched over; they're distinct from the model's learned *parameters* (the coefficients themselves), which come *from* training data.

**Actual result** (see `model/evaluation_results.json`'s `"hyperparameter_tuning"` field):

| C | Mean CV Accuracy |
|---|---|
| 0.1 | 0.9341 |
| 1 | 0.9574 |
| 5 | 0.9567 |
| **10** | **0.9595 (best)** |
| 20 | 0.9581 |

The best value found was **C=10**, a mild improvement over the scikit-learn default of C=1. Since Random Forest (not Logistic Regression) won the overall model comparison this run, this tuned Logistic Regression isn't the deployed model — it's reported for demonstration, exactly as the methodology intends (tuning always runs, but is only *applied* to the deployed model when Logistic Regression is the winner).

## 13. Evaluation

Metrics used, and why each one matters — genuinely important here, since the dataset is imbalanced:

- **Accuracy** — overall % correct. Can be misleading on imbalanced data: a model could look good just by favoring the majority classes.
- **Precision / Recall / F1 (weighted)** — precision asks "of everything predicted as X, how much really was X"; recall asks "of everything that really was X, how much did we catch"; F1 is their balance. **Weighted** averaging weights each class by how many samples it has — so it can hide poor performance on small classes.
- **Precision / Recall / F1 (macro)** — the same three metrics, but every class counts equally regardless of size. This is the number that would expose a model doing great on Software Engineer (300 rows) but badly on UX Designer (120 rows). On this dataset macro F1 (0.9613 for the deployed model) and weighted F1 (0.9616) stay close, which itself is informative: it means the model isn't systematically favoring the majority classes.
- **Confusion Matrix** — shows exactly which careers get mixed up with which, not just a single number (see Section 14).
- **Baseline comparison** — a "majority-class" baseline (always guess Software Engineer, the biggest class) scores 0.1648 on this dataset — notice this is higher than 1/9 (0.111) specifically *because* the dataset is imbalanced. The trained model's 0.9615 is a genuine +0.7967 lift over that floor.

> **Note on class weighting**: `class_weight="balanced"` was also tested against the default during development (see `/evaluate`'s collapsed "Advanced / optional analysis" section and `model/evaluation.py`'s `compare_class_weights()`). It didn't clearly help on this dataset, so it isn't part of the main evaluation story here — kept in the code and in the JSON output for completeness, not removed.

## 14. Error Analysis

With the rebuilt, overlapping-vocabulary dataset, the deployed model makes **14 errors out of 364 test examples (3.85%)** — a genuinely non-zero, genuinely interpretable error rate (computed by `python -m model.error_analysis`, which re-derives the exact same train/test split used in training and inspects the saved model's actual predictions). Every error is a specific (true → predicted) career pair, not random noise:

| True → Predicted | Count |
|---|---|
| Back-End Developer → DevOps Engineer | 3 |
| Data Analyst → Machine Learning Engineer | 2 |
| Machine Learning Engineer → Data Analyst | 2 |
| Software Engineer → Front-End Developer | 2 |
| UX Designer → Front-End Developer | 2 |
| Data Analyst → Business Analyst | 1 |
| DevOps Engineer → Software Engineer | 1 |
| Product Manager → Business Analyst | 1 |

**These are exactly the career pairs the dataset was deliberately built to overlap** (Section 4b) — which is itself a meaningful validation that the confusion is coming from genuine skill ambiguity, not a bug. A representative example: a test row with skills `python, data cleaning` and interests `innovation, pattern recognition` (true career: Machine Learning Engineer) was predicted as Data Analyst with 57% confidence, vs. only 40% confidence in the true class — genuinely ambiguous, since neither "python" nor "data cleaning" is exclusive to ML Engineer in this dataset. The **minority class** (UX Designer, 24 test samples) had 2 errors — an 8.3% error rate, somewhat higher than the overall 3.85%, consistent with it being the smallest class.

Where there are very few errors for a given class, `model/error_analysis.py` also reports the model's **lowest-confidence predictions overall** (correct or not) — these surface ambiguous profiles even when the model happened to guess right.

## 15. Model Interpretability

For Logistic Regression specifically (when it's the deployed model), each input word/category has a learned weight per career — shown on the `/evaluate` page as "top terms per career". Random Forest (the current deployed model) doesn't expose this kind of per-class linear weight, so this table is only shown when a linear model wins the comparison — a real, disclosed limitation of tree-based models rather than something faked.

This same underlying idea also powers the **skill and interest matching** shown on the `/predict` and `/skills` pages, alongside the top-3 **alternative career predictions**:
```
Predicted Career: Data Analyst
Relevant skills you have: SQL, Python, Excel
Missing skills (commonly used in this career): Power BI, Tableau
Relevant interests you have: data, analytics
Alternative careers (next-highest predicted probabilities): Business Analyst, Machine Learning Engineer
```
**Important**: the matching/missing-skill and matching-interest logic is a simple **dataset lookup** (count how often each skill/interest appears in that career's training rows), not a second ML model. Only the career prediction itself (and its ranked alternatives/confidence) comes from the trained classifier. The app never claims a feature "caused" the prediction — wording throughout is "these features contributed strongly to the model's classification," consistent with what a learned probability actually represents.

## 16. What-If Analysis

On the `/predict` page, after getting a prediction, the person can add a skill and re-run the prediction to see if it changes:

```
Before: Python + SQL + Excel           → Data Analyst
After adding: Machine Learning, Stats  → prediction/confidence may shift
```

This simply re-runs the same trained model with modified input — it is **not** causal analysis (adding a skill doesn't *cause* a career outcome), just a way to explore how sensitive the model's prediction is to specific skills. Verified working end-to-end against the retrained model (see Section 25, Final Testing, in PROJECT_EXPLANATION.md).

Already described in Section 15 — worth repeating clearly: **the roadmap and skill recommendations are rule-based, not ML-generated.** The flow is:

## 18. Limitations

Honest, in plain language:

1. **The dataset is synthetically generated for educational purposes.** It was built from hand-curated skill/interest pools with deliberately engineered overlap (Section 4b), not real job postings or resumes. It does **not** represent actual employment statistics or real hiring demand.
2. **The class distribution is a design choice, not a market signal.** The imbalance (16.5% down to 6.6%) was chosen to create a genuinely imbalanced *classification problem* to practice on — it must not be read as a claim about which careers are more in-demand in reality.
3. **Career categories overlap in real life far more than any fixed skill-pool design can fully capture.** The overlap mechanism here (primary/overlap/universal pools + random cross-career noise) is a reasonable approximation, not a simulation of the real world.
4. **Limited dataset size (1,820 rows) and small number of career categories (9)** — doesn't represent the full job market.
5. **Real-world performance may differ, likely for the worse.** Real candidates' skill/interest text would be messier, more inconsistently phrased, and have overlap patterns this generator didn't anticipate. The ~96% test accuracy reported here is a property of this specific synthetic dataset, not a guarantee about real-world data.
6. **Model confidence is not the same as actual career suitability, and predictions are recommendations, not guarantees.** A confidence score reflects how strongly the input matches statistical patterns in the training data — it says nothing about whether someone would actually succeed in or enjoy that career.
7. **No geographic or temporal data** — salaries assume one implicit market and don't change over time.
8. **Salary figures are dataset lookups, not predictions.** No regression model estimates salary; it's just min/max/average from matching rows in the training data, and salary is never used as a model input feature (avoiding any leakage risk from it).
9. **Recent predictions are shared across all users** (a single in-memory list for the demo), not tied to individual user accounts.
10. **A larger, real-world dataset would be required for any production use of a system like this.**

Realistic next steps, roughly in order of value:
